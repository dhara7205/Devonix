# Threats → Concrete countermeasures (detailed)

## A. Tampering / reverse engineering (someone modifies your EXE to bypass licensing)

**Why dangerous:** local-only checks are trivially bypassed if attacker can change binary or read license format.
**Defenses:**

* **Code signing (Authenticode / EV code signing):** Sign installers & executables so OS shows “publisher verified” and tamper is detectable. Use a trusted CA (DigiCert, Sectigo, SSL.com). This is table-stakes for enterprises. ([DigiCert][1], [Sign My Code][10])
* **License file cryptographic signatures:** License files signed by your private key. App verifies using embedded public key. Tampered license = invalid.
* **Binary integrity checks:** App verifies its own checksums at runtime, and validates important files (ASAR, native libs).
* **Obfuscation / native module for sensitive logic:** Keep critical checks out of plain JS. Use native compiled modules (C/C++/Rust) for license verification or use bytecode compilers; apply JS obfuscation/ASAR protection for Electron. This raises the bar (not perfect). ([electron-vite.org][11], [Stack Overflow][12])
* **Tamper detection & response:** If tamper detected, lock down features, require admin re-auth, or show visible warning.
  **MVP focus:** code signing + signed license files + basic obfuscation.

## B. License/key sharing & over-usage

**Why dangerous:** a single small-biz license used by many, kills revenue.
**Defenses:**

* **Bind license to company metadata:** company name, allowed domains, install\_id, and (optionally) HW fingerprint. Require admin approval (confirmation email to [admin@company.com](mailto:admin@company.com)).
* **Local registry + distinct user tracking:** record unique user IDs (SSO subject or email) and enforce `max_users` during login.
* **Periodic server validation (phone-home):** app sends minimal signed report (install\_id, current\_user\_count, timestamp). Server can mark overuse and notify admin/sales. Make this interval configurable and provide offline grace. (Be explicit in privacy docs).
* **Concurrent session limits & rate limits**: enforce concurrent login thresholds in addition to distinct user counts.
  **MVP focus:** local registry + signed license + optional weekly phone-home with grace.

## C. Credential exposure (you storing customer passwords)

**Why dangerous:** storing passwords makes you a target and creates liability.
**Defenses:**

* **Prefer SSO/OIDC/SAML/LDAP:** enterprises usually prefer federation; you avoid storing passwords. Use open source (Keycloak) or trusted vendors (Auth0). ([Tesseral][2], [SSOJet][3])
* **If you must store:** use Argon2/bcrypt, strong salt, enforce complexity, account lockout, and store in an encrypted DB or OS credential store. Better: use HashiCorp Vault or OS keystore to store secrets. ([My blog][4])

## D. Data exfiltration (Devonix accidentally sends company code offsite)

**Why dangerous:** trust breaker; enterprise deal killer.
**Defenses:**

* **Design promise:** default *all processing on-premises*. Telemetry must be minimal & explicit.
* **No raw code offsite:** if any optional cloud feature exists, make it opt-in and clearly show what is sent, with UI consent.
* **Transport & storage encryption:** TLS for any network comms, encryption at rest (AES with KMS or local key).
* **Log scrubbing & redaction:** never log raw customer code or secrets. Provide log redaction utility.
  **MVP focus:** default local-only, telemetry opt-in, TLS.

## E. Supply-chain & dependency risks

**Why dangerous:** vulnerable libs create RCE/XSS/other holes.
**Defenses:**

* **SAST & dependency scanning:** integrate Snyk, Dependabot, or SonarQube into CI. ([Mend.io][5], [Solutions Review][13])
* **DAST before release:** run OWASP ZAP / Burp Suite scans on frontend/backend. ([OWASP][6], [Beagle Security][7])
* **Minimal third-party code in runtime paths** and routine dependency updates.
  **MVP focus:** automated dependency scanning + weekly/CI SAST.

## F. Remote exploitation (APIs / local admin pages exposed)

**Why dangerous:** misconfigured networking can expose admin API externally.
**Defenses:**

* **Bind to localhost by default**; document explicit steps for opening ports.
* **Mutual TLS or token auth** for any remote admin access. Use firewall & service account authentication.
* **RBAC & least privilege** for APIs.
  **MVP focus:** localhost binding + admin UI password + RBAC.

## G. Plugin / extension abuse (if you allow plugins)

**Why dangerous:** plugins can execute arbitrary code.
**Defenses:**

* **Sandbox plugin runtime** (run in separate processes / restricted containers).
* **Whitelist plugin capabilities & require code review for third-party plugins.**
  **MVP focus:** disallow third-party plugins until you build sandboxing.

## Stage 3 — JIT provisioning + seat enforcement

* Sequence on successful SSO callback:

  1. Lookup user by `sso_sub` or `email`.
  2. If user exists and `active` → allow sign-in. Update `last_seen`.
  3. If user does not exist → check license (`active_count < max_users`).

     * If seat available → create user record, assign default role (e.g., `developer`), increment provisioned count (or derived). Log provisioning. Issue app session.
     * If seats exhausted → block provisioning and return a friendly message (`"seats_full"`). Log attempt.
* Implement server-side session issuance (short JWT + refresh token stored hashed in `sessions`).

**Deliverable:** SSO login can create an account if seat available; blocked if full.
**Acceptance:** new user record is created and session returned on success; blocked when seat cap reached.

## Stage 4 — Sessions & session revocation

* Short-lived JWTs for API auth; refresh tokens persisted server-side (hash).
* On deactivation: revoke refresh tokens and mark active=false. Ensure middleware rejects requests for deactivated users even with valid JWT.
* Endpoint: `POST /auth/refresh` (refresh JWT using server-side refresh token).

**Deliverable:** secure session flow + revocation support.
**Acceptance:** after deactivation, requests fail; refresh token invalidated.

  * `POST /admin/roles/assign` — assign role to user (Admin-only).
  * `GET /admin/usage` — `active_count / max_users`.

**Deliverable:** admin can manage users and roles via APIs.
**Acceptance:** role assignment persists; role checks enforced on protected endpoints.

**Deliverable:** role enforcement works across endpoints.
**Acceptance:** protected endpoints reject non-role users.
